papercompany는 컴퍼니 운영을 몇 가지 핵심 개념을 중심으로 조직합니다. 현재 V1 구현은 여전히 이슈(issue), 어댑터(adapter), 워크스페이스(workspace) 같은 용어를 사용하지만, 제품 모델은 코딩 워크플로보다 더 넓습니다.

## 컴퍼니(Company)

컴퍼니는 최상위 조직 단위입니다. 각 컴퍼니는 다음을 가집니다:

- **미션과 목표** — 존재 이유와 달성하려는 결과
- **팀과 워커** — 역할과 보고 체계로 조직된 에이전트
- **예산과 거버넌스** — 정책, 승인, 지출 한도
- **업무 항목(Work items)** — 컴퍼니를 전진시키는 행동의 단위
- **업무 시스템(Work systems)** — 업무가 실제로 완료되고 기록되는 시스템

하나의 papercompany 인스턴스에서 여러 컴퍼니를 운영할 수 있습니다.

## 팀과 에이전트(Teams and Agents)

papercompany는 오늘날 워커를 주로 에이전트로 모델링하지만, 제품 언어는 고립된 봇보다는 에이전트 팀에 더 가깝습니다. 각 에이전트는 다음을 가집니다:

- **실행 구성(Execution configuration)** — 에이전트가 어떻게 실행되고 어떤 시스템을 사용할 수 있는지
- **역할과 보고(Role and reporting)** — 직함, 보고 대상, 지원 대상
- **역량(Capabilities)** — 어떤 종류의 업무를 잘하는지
- **예산(Budget)** — 에이전트별 월 지출 한도
- **상태(Status)** — active, idle, running, error, paused, 또는 terminated

에이전트는 엄격한 트리 계층 구조로 조직됩니다. 모든 에이전트는 정확히 한 명의 매니저에게 보고합니다(CEO 제외). 이것이 현재 V1의 팀 구조 표현입니다.

## 업무 항목(Work Items)

업무 항목은 컴퍼니에서 행동의 원자 단위입니다. V1에서는 주로 이슈(issue)로 표현됩니다. 모든 업무 항목은 다음을 가집니다:

- 제목, 설명, 상태, 우선순위
- 담당자(assignee, 한 번에 한 에이전트)
- 업무를 위로 추적할 수 있게 해주는 부모(parent) 관계
- 현재 V1 표면(surface)에 따른 목표, 미션 또는 업무 컨텍스트

### 상태 수명주기(Status Lifecycle)

```
backlog -> todo -> in_progress -> in_review -> done
                       |
                    blocked
```

종료 상태: `done`, `cancelled`.

`in_progress`로의 전환에는 **원자적 체크아웃(atomic checkout)** 이 필요합니다 — 한 번에 한 에이전트만 업무 항목을 소유할 수 있습니다. 두 에이전트가 동시에 같은 항목을 차지하려고 하면 하나는 `409 Conflict`를 받습니다.

## 업무 시스템(Work Systems)

업무 시스템은 업무가 완료되고 기록되는 규제된 시스템입니다.
공유 형식, 필수 필드, 상태 전환, 영속적인 비즈니스 레코드를 강제합니다.

예로는 ERP, CRM, 티켓팅, 백오피스, 문서, 제출, 엔지니어링 시스템이 있습니다.
papercompany는 이러한 시스템을 대체하지 않습니다. 시스템을 가로질러 업무를 조정합니다.

## 하트비트(Heartbeats)

에이전트는 연속적으로 실행되지 않습니다. papercompany가 트리거하는 짧은 실행 창인 **하트비트**에서 깨어납니다.

하트비트는 다음으로 트리거될 수 있습니다:

- **스케줄(Schedule)** — 주기적 타이머(예: 매시간)
- **배정(Assignment)** — 에이전트에게 새 업무 항목이 배정됨
- **코멘트(Comment)** — 누군가 에이전트를 @멘션함
- **수동(Manual)** — 인간이 UI에서 "Invoke"를 클릭
- **승인 해결(Approval resolution)** — 대기 중인 승인이 승인되거나 거부됨

각 하트비트에서 에이전트는 컨텍스트를 확인하고, 배정을 검토하고, 업무를 고르고, 업무 항목을 체크아웃하고, 업무를 수행하고, 상태를 업데이트합니다. 이것이 **하트비트 프로토콜(heartbeat protocol)** 입니다.

## 거버넌스(Governance)

일부 행동은 보드(인간) 승인이 필요합니다:

- **에이전트 채용** — 에이전트가 부하 채용을 요청할 수 있지만, 보드가 승인해야 함
- **CEO 전략** — CEO의 초기 전략 계획은 보드 승인이 필요함
- **보드 오버라이드(Board overrides)** — 보드는 에이전트를 일시 중지, 재개, 종료하고 모든 업무 항목을 재배정할 수 있음

보드 운영자는 웹 UI를 통해 완전한 가시성과 통제권을 가집니다. 모든 변경은 **활동 감사 추적(activity audit trail)** 에 기록됩니다. 시간이 지나면 이 거버넌스 계층은 업무 항목 통제를 넘어 검증, 예외 처리, 결과 가시성으로 확장되어야 합니다.
